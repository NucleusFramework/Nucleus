# AOT cache vs installers

**AOT cache vs installers** (#748 follow-up): the JDK refuses the whole AOT cache when any classpath JAR's size **or mtime** differs from training (enforced since JDK-8377932: 25.0.4 / 26.0.2 / 27; 25.0.1 and 26.0.1 silently accept, so test on a recent JDK). electron-builder builds the NSIS payload with `7z -mtm=off`, so installed files get the install time: before the fix no NSIS install ever used its cache. `AotJarTimestamps` pins the JARs to 1980-01-01T00:00:02Z right before training (after the unsealing, the last JAR rewrite) and the installer's `customInstall` pins them back (`nucleusPinAotJarTimestamps`, `SetFileTime` via NSIS's System plugin; a user `nsis.includeScript` with its own `customInstall` must insert it, the task warns; the macro is always defined — empty without a cache — so such a script still compiles with AOT off). Nothing may rewrite a JAR after training — that is why DLLs inside JARs are signed by the AOT task (both the regular and the sandboxed one), not the package task; a dev run (only `run*` tasks requested, as for the GraalVM quick build) skips that signing, and the `signJarLibraries` input makes the next packaging run train again on signed JARs. Verified on an installed app with MS OpenJDK 25.0.4: 2840 app classes from the cache vs 0 with install-time mtimes. Not covered: the portable `Exe` target (extracts to a temp dir at each launch) and ZIP (DOS local time). GraalVM runtimes enable JVMCI by default, whose implicit `jdk.internal.vm.ci` module the single-step workflow's assembly JVM loses (`jdk.module.addmods` mismatch → archived module graph disabled); the AOT task probes `EnableJVMCI` and hands the module to the child through `JDK_AOT_VM_OPTIONS` (probed with the app's own options, so `-XX:-EnableJVMCI` is honoured)
