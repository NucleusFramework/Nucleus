# Windows session end (#751)

**Windows session end** (#751): logoff / restart / shutdown and Restart Manager closes (`ENDSESSION_CLOSEAPP`, i.e. installers) go through the same cancelable `requestQuit` as macOS Cmd+Q (#696), so `onCloseRequest` can veto them and `isQuitting` is `true`. Every tao window (app windows *and* the thread target) hands `WM_QUERYENDSESSION` / `WM_ENDSESSION` to `platform/windows/end_session.rs`: one app window answering TRUE on its own is enough for the Restart Manager to start ending the process. The query is answered synchronously (`TaoApplication.queryEndSession`: AGREE = every window agreed during the call, HOLD = quit still in flight → FALSE + `ShutdownBlockReasonCreate` on the thread target, released by a veto, REFUSE = a window already stayed open), and native reuses one answer for 1 s so a session end asks the app once. On AGREE nothing has closed and the app does **not** exit: Windows may still cancel (another app refuses, the user cancels, an installer aborts), so the exit waits for `WM_ENDSESSION` — FALSE calls the quit off (`SessionExit.Cancelled` if its settle is still pending), TRUE tears down. A window that closed itself during its close request (HOLD) stays closed — asking is closing with this API, the price of a veto. A Restart Manager close (`ENDSESSION_CLOSEAPP`, an installer) waits for nobody, so HOLD would read as a refusal: with that flag the query drains the Compose main queue for up to 2 s (`settleQuitNow` → `TaoMainDispatcher.pump()` only, no Win32 message pumped, so no #640 re-entrancy) and a window closing through recomposition (`isOpen = false`) answers AGREE. Native passes `END_SESSION_FLAG_REFUSED` when Windows already got a FALSE without Kotlin being asked (deferred query, AWT forward that timed out): an AGREE then becomes HOLD and the app exits by itself. An AGREE with no `WM_ENDSESSION` within 15 s is treated as cancelled (generation-guarded), so `isQuitting` cannot stay stuck. `ENDSESSION_CRITICAL` asks no window (AGREE at once). The AWT behaviour (class `SunAwtToolkit`, JVM ended by its query handler) was checked on JDK 17, 21, 25 (HotSpot and OpenJ9), 26 and 27-ea. A query re-entering `queryEndSession` from a close request that pumps (native dialog, AWT's forward) answers HOLD, and the outer AGREE then becomes HOLD too (Windows already has a FALSE, so the app exits by itself); after an AGREE, later queries of the same session end are answered AGREE without asking again; a cancel arriving inside a nested pump is delivered later through `UserEvent::SessionEndCancelled`. The teardown calls `exitProcess` from the UI thread: an app shutdown hook that waits for work posted to `Dispatchers.Main` blocks until Windows kills the process. `WM_ENDSESSION(TRUE)` tears down **synchronously** (composition dispose, then every window's `destroyed()` — scenes are otherwise disposed on the async native `DESTROYED` — then `exitProcess(0)`): Windows may kill the process once it returns. Neither is delivered into Kotlin while tao's handler is on the stack (`should_buffer`; the query is deferred via `UserEvent::QueryEndSession` and the session held). `call_kotlin` must not hold `EVENT_CALLBACK` across the call — app code can cause a synchronous tao event whose `dispatch` locks it (deadlocked `nativeUninstallDecoration`'s `SetWindowPos`). **AWT**: Compose initializes AWT under Tao (RectManager → skiko `SwingDispatcher`), and AWT's hidden `SunAwtToolkit` window, on its own thread, ends the JVM as soon as *its* `WM_QUERYENDSESSION` handler runs (shutdown hooks, exit code 143), whatever the app answered. `awt_session.rs` subclasses it (WinEvent hook on creation): queries get the app's answer (cached, else forwarded to the thread target — the close requests run inside that wait, so it is bounded at 30 s, not 3, and `SMTO_ABORTIFHUNG` refuses at once only if the loop is *already* hung when the query arrives; it does not abort mid-wait), `WM_ENDSESSION` is forwarded asynchronously, AWT never sees either (a synchronous forward would deadlock against AWT's `ToolkitShutdown` hook). Testing: `RmShutdown` (no force) against the **packaged** exe launched through ShellExecute — under `gradlew run`, or with an inherited console, RM classifies the JVM as `RmConsole` and Ctrl+C's it — and target the JVM pid, not the jpackage launcher parent (it restarts itself as a child). A real logoff was not exercised.

## Pitfalls found in E2E

- **The Restart Manager settle drains, it does not pump.** `settleQuitNow` runs the Compose main queue with `TaoMainDispatcher.drain()`, never `pump()`: `pump()` reopens the wake gate and arms a (throttled) `nativeWake` whenever work is left, and nothing coalesces wakes natively. Called once per millisecond while an animation keeps the queue busy, each call left one more wake behind, and each of those re-armed itself from then on — after a few hundred Restart Manager queries the loop pumped dozens of times per frame and a posted `WM_CLOSE` took ~700 ms to reach `onCloseRequest`.
- **A forward from AWT must never outlive the loop.** If a query reaches AWT's toolkit window while the app is already quitting on its own, the forward to the thread target waits on a loop that no longer pumps, and AWT's `ToolkitShutdown` hook waits for that thread: the exit stalled for up to 30 s and the Restart Manager got a refusal from an app that was leaving. Once the loop has returned (and before the `WM_ENDSESSION(TRUE)` teardown) `end_session::stop_answering` makes every query agree and serves the forwards already in flight with `PeekMessage(PM_QS_SENDMESSAGE)`; `begin_forward` / `end_forward` count them (`SeqCst`, so a forward either sees `EXITING` or is counted).
