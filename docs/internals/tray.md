# tray internals

`tray` - system tray icon + native menu (`Tray(…)` composables, the `TrayMenuBuilder` / composable `ComposableTrayMenuScope` DSL) and `TrayApp` (an icon whose click toggles a popup anchored to it). Imported from NucleusFramework/ComposeNativeTray; one module, package `dev.nucleusframework.tray`, natives `nucleus_tray`.

## Shared design

- `NativeTray` drains one **conflated** queue on one worker: changes reach the backend in order and a burst collapses to its newest state. `dispose()` is final (a lock + `disposed` flag): no queued or in-flight change can recreate the icon.
- Composable icons are rendered to files (backends take paths) through `IconFileCache`: content-addressed (identical renders share a file) and capped at 64 files (`-Dnucleus.tray.iconCacheSize`). Each render used to be a new temp file kept until JVM exit.
- A change carrying the `iconKey` of the icon already shown skips rendering, so a menu-only change is immediate.
- Callbacks are stable wrappers over the **latest** lambdas (`rememberUpdatedState`): `primaryAction` / `onMenuOpened` captured values never go stale, and a fresh lambda per recomposition no longer re-applies the tray. A composable-menu click resolves its handler in the latest recording by item path, since the native menu is only rebuilt when the structure changes.
- `jni_utf8.h` (shared by every bridge) encodes real UTF-8 and **drops** U+0000 (it used to truncate, losing e.g. the shortcut hint after it). `src/main/native/shared/**` is an input of every `buildNative*` task.

## Windows

- One tray = one daemon thread (`NucleusTray-<id>`) that owns the hidden window (`NucleusTrayWindow`, top-level so it still receives `TaskbarCreated`), the HMENU and the HICON. The context hangs off `GWLP_USERDATA`: no process-wide list, no lock, so an open popup menu (`TrackPopupMenu` runs a modal loop) on one tray never stalls another. Callbacks are JNI global refs stored on their tray / menu item, never in a shared list (disposing a tray used to drop every other tray's menu callbacks).
- The loop sleeps in `MsgWaitForMultipleObjectsEx`; other threads publish the wanted state and post `WM_TRAY_WAKE` (no 50 ms polling).
- `tray_wake(cancel)` (dispose) sets `closing` from any thread: no menu opens any more, the pump stops, and an open menu gets `EndMenu`. Without it a backlog of queued clicks reopened a modal menu after dispose and pinned the thread forever.
- Menu labels are shown literally: `&` is doubled (it was eaten as a mnemonic), dividers are a flag (a `-` label used to become a separator), empty labels are kept. Command ids index a per-rebuild table; every bitmap (submenus included) is freed on rebuild (8 GDI objects leaked per rebuild before).
- Checkable items are patched by an identity token, not by label (two items sharing a label used to toggle together).
- A bad icon path keeps the current icon; `TaskbarCreated` (explorer restart, DPI change) reloads the icon at the current `SM_CXSMICON` and re-adds it. A shutdown hook removes icons when the JVM exits without disposing.

## E2E (Windows)

`./gradlew :tray:test` (headful: real notification area, no mouse). Black-box through Win32 from the test JVM (JNA, tests only): the hidden window gets the very messages the shell sends (`WM_APP+1` with `WM_LBUTTONUP` / `WM_RBUTTONUP`, `WM_COMMAND`, `TaskbarCreated`), the popup is read back from the `#32768` window with `MN_GETHMENU`, icons are checked with `Shell_NotifyIconGetRect`, leaks with `GetGuiResources`.

- `WindowsTrayTortureTest`: seeded menu fuzzer (hostile labels, nesting, 0-80 items; compares the popup item by item), multi-tray isolation, frozen-tray, throwing callbacks, explorer restart, GDI leak, lifecycle churn across threads, dispose racing init, rapid-update convergence, garbage icons.
- `WindowsTrayLifecycleTortureTest`: JVM exit with a live tray (child JVM), dispose with the menu open, click storm during rebuilds and disposals, 30 trays, icon-file growth, evicted icon file, create/dispose x100 leak check.
- `WindowsComposeTrayTortureTest`: the composables in a real composition (`ImageComposeScene`, two render passes per frame: a composable menu re-records into its scope's snapshot list and `Tray` recomposes on the next pass): labels follow state, stale-closure clicks and `onMenuOpened`, add/remove from composition.
- `WindowsTrayAppE2ETest`: each scenario runs `TrayAppProbeMain` in its own JVM (real `nucleusApplication`, Tao loop, standalone popup) and reports `CHECK` lines: click toggles, `visibleOnStart`, seeded click storm and concurrent `show`/`hide`/`toggle` (state must match the popup on screen), resize while visible, menu next to the popup, removal from composition. Geometry oracle: the popup's physical rect has the state's dp size at the window DPI, sits inside the icon monitor's work area, against the taskbar edge (default 10 px offset), centered on the icon unless clamped. `TrayApp` hands the tray a stable primary action, so a show/hide no longer rebuilds the native tray.

- `TrayAppFuzzMain` (same harness): `fuzz` / `multi` run N seeded rounds of random actions on one or two `TrayApp`s (tray clicks, `show`/`hide`/`toggle`, 3-thread bursts, sizes from 1x1 to 5000 dp, offsets ±600, icon / tooltip / menu changes, `dismissMode`, a ticking content, outside clicks, removal and reinsertion), then check: state matches the screen, a popup that fits stays in the work area (a larger one keeps its top-left corner on screen), anchored to its own icon without offsets, GDI/USER counts and tray threads bounded. In `multi` each app owns distinct sizes so a popup on screen always says whose it is. `dismiss`: AUTO hides on an outside click, a click within 200 ms of the show is ignored, the icon re-click while open closes and stays closed, MANUAL ignores outside clicks. Outside clicks are delivered by posting `WM_APP + 0x51` (what Tao's `WH_MOUSE_LL` hook posts) to the popup, so the real mouse never moves.
- Fixed by the fuzz: a show blocked or hidden before it consumed its pre-computed position left it behind, and a later show after a resize reused the old size's position (a 900 dp popup opened at y = 0, half off the work area); the pending position is now keyed by size and offsets. The corner fallback (no click recorded yet, e.g. right after reinsertion) did not clamp, so a popup wider than the screen lost its left half; every placement now goes through one clamp. A resize or offset change landing while a show was still resolving its position (~400 ms on Windows) was dropped: the re-anchor effect is now also keyed on the popup coming up. With no click recorded, the position is read from the shell on demand instead of guessing a corner, and the Windows corner comes from the taskbar edge (`ABM_GETTASKBARPOS`, RTL-aware): `TrayNotifyWnd` no longer locates the notification area on Windows 11, which made the guess bottom-left.

- `realmouse` (same harness): real `SendInput` clicks through Tao's `WH_MOUSE_LL` hook, aimed at a topmost window the child JVM owns (never another app), cursor restored: a click elsewhere hides (AUTO), a click inside keeps, MANUAL ignores.
- `WindowsPopupPlacementTest`: `windowsPopupOrigin` (the pure Windows placement) for every scale from 100 to 350 % and every taskbar edge, LTR and RTL, with the anchor computed like `tray_get_notification_icons_position`: in the work area, never over the icon, against the taskbar, centered unless clamped; plus 20 000 seeded screens / sizes / offsets that must stay in the work area (or keep the top-left of an oversized popup).

Not covered on a real screen: HiDPI and top/side taskbars (the dev machine is 100 %, bottom taskbar); the placement math is covered by the pure test, the dp-to-pixel conversion of the popup is Tao's.

Seeds are printed (`[torture] … seed=`); rerun with `-PtraySeed=<seed>`, scale with `-PtrayIterations=<n>`. Dismiss popups with `WM_CANCELMODE` only: `#32768` windows are reused, so a stray Esc closes the next popup. `Shell_NotifyIconGetRect` fails for a dead window, so it cannot tell a removed icon from a visual ghost.

## macOS

`nucleus_tray_macos.m` (Objective-C, ARC; the Swift + C-struct bridge it replaces read menu structs the JVM had already freed: two quick menu updates crashed the JVM).

- **Message passing.** `nativeSubmit` gets the whole state (icon, tooltip, callbacks, the menu flattened in pre-order with depths) and turns it into immutable Objective-C objects on the calling thread; the main thread applies the newest one (conflated, like Windows). AppKit never reads JVM-owned memory, each callback is a JNI global ref owned by its `NTCallback` (released with the menu that holds it), and no call waits for the main thread, so a caller holding a lock the main thread needs cannot deadlock.
- Work reaches the main thread with `CFRunLoopPerformBlock` in the common modes (each block in its own autorelease pool: a plain JVM's main loop drains none), so updates and disposals apply while a menu tracks.
- **Menus.** Left click without a primary action, right click or Ctrl+click open the menu (`statusItem.menu` set around `performClick:`). A click while a tray menu is up only closes it, as AppKit does with a real click: opening a second menu inside the first one's tracking loop orphaned the outer session and left the main thread in `NSEventTrackingRunLoopMode` for good. AppKit presents the menu asynchronously and drops a cancel that lands meanwhile, and a menu left tracking blocks every other menu of the system: a cancel (dispose included) is retried every 50 ms until the menu is closed. The tray is retained for the whole tracking (`objc_precise_lifetime`): a dispose landing while its menu was open freed it under `popUpMenu`'s frame.
- Items under a disabled submenu read back as disabled (AppKit derives it). Separators are a flag, labels are literal, checkables are patched by identity token, a bad icon path keeps the current icon.
- **Geometry.** Positions are cached under a lock, refreshed on the main thread (apply, click, window move / screen notifications, and every query: off the main thread the query answers from the cache and schedules a refresh). A visible `TrayApp` popup re-reads its item every 250 ms: the item slides whenever another menu-bar item comes or goes. The status item's window is drawn by the system menu bar on macOS 26+ and never shows in `CGWindowList`; a new item may take seconds to be placed after a burst of others.

### E2E (macOS)

`./gradlew :tray:test` with `MallocScribble=1` (a use after free crashes instead of reading stale values). Real `NSStatusItem`s; the test hooks (`MacTrayInitializer.debug*`) read AppKit's own state (button, tooltip, `NSMenu` tree, open menu, main run-loop mode), select items with `performActionForItemAtIndex:` and click through the button's own action: the item's window belongs to the system menu bar, no event reaches it from inside the process. The click hook runs from a one-shot timer, never a perform block (a menu opened from a perform block holds back every block queued behind it, cancels included) and calls the tray unretained, like AppKit with its weak target.

- `MacTrayTortureTest`: seeded menu fuzzer (shared `MenuFuzzer`), callbacks of fuzzed items, multi-tray isolation, updates and creation while another tray's menu tracks, primary / menu clicks, throwing callbacks, duplicate checkable labels, reported position, lifecycle churn, dispose racing creation, rapid updates, garbage icons, callbacks released (weak references collected).
- `MacTrayLifecycleTortureTest`: dispose with the menu open, a click while a menu is open, a callback disposing its own tray, click storm with rebuilds and disposals, 30 trays, create/dispose x100, JVM exit with a live tray and an open menu, position across rebuilds. Every test ends with no status item alive (counted through weak references; status-bar windows are no oracle in a plain JVM).
- `MacTrayAppE2ETest`: `MacTrayAppProbeMain` in its own JVM (`nucleusApplication`, Tao); the popup is read from `CGWindowListCopyWindowInfo` (own windows need no Screen Recording permission; the panel sits at the pop-up menu level, told apart by its size): click toggles, `visibleOnStart`, click storm, concurrent `show` / `hide` / `toggle`, resize, menu, removal; `fuzz` / `multi` with sizes 1x1 to 5000, offsets, tooltips, menus, ticking content, dismiss mode, removal and reinsertion. Oracle: size, top right below the menu bar plus the vertical offset, centered on the icon (offset away from the nearer edge) or clamped, inside the work area.

A JVM that crashes leaves `~/Library/Application Support/CrashReporter/java_<uuid>.plist`; until it is moved away every java process that starts `NSApp` hangs in a modal "reopen windows?" alert (only `sample` shows it).

Not covered: outside-click dismissal with a real mouse, multiple displays.

## Linux

`nucleus_tray_linux.c` (C, sd-bus): a StatusNotifierItem with a `com.canonical.dbusmenu` menu. It replaces `sni.c` + `jni_bridge.c`, ported from ComposeNativeTray, whose model the torture suite broke in several places (below).

- **One tray = one thread + one bus connection + one name.** Each tray owns a daemon thread (`NucleusTray-<n>`, attached to the JVM), its own sd-bus connection and its own well-known name `org.kde.StatusNotifierItem-<pid>-<n>`; its `Id` is `<appId>-<trayId>`. Only that thread touches the bus: no bus lock, so no upcall can deadlock against one. A panel restart (new `org.kde.StatusNotifierWatcher` owner, seen through `NameOwnerChanged`) registers the item again; registration is asynchronous, so a missing watcher never stalls the loop.
- **Message passing.** `nativeSubmit` turns the whole state (icon file, tooltip, callbacks, the menu flattened in pre-order with depths) into an immutable `nt_state` on the calling thread; the loop applies the newest one (conflated) and tells the host only what changed: `NewIcon`, `NewToolTip` / `NewTitle`, `PropertiesChanged`, and for the menu either nothing (same menu), `ItemsPropertiesUpdated` (same structure, new label / enabled / check state: an open menu stays open) or `LayoutUpdated`. Menu ids are pre-order positions, so an unchanged menu keeps its ids. A menu is never visible half-built.
- **Callbacks** are JNI global refs owned by the state that carries them: per tray, per item, released when the state is replaced or the tray closes. The loop calls them directly; `LinuxTrayManager` hands them to `Dispatchers.IO` at once, so a callback may update or dispose its own tray. A click reaches an item only if a user could make it: the id exists in the current menu, it is a plain or checkable entry, enabled, and every submenu above it is enabled.
- `ItemIsMenu` is true only without a primary action: with it, the host calls `Activate`, whose position is recorded per tray (`TrayClickTracker.recordClick(instanceId, …)`), so two `TrayApp`s anchor to their own icon. `onMenuOpened` fires on `AboutToShow(0)` or `Event(0, "opened")`, once per opening (300 ms debounce, also after our own layout updates: hosts re-ask after one).
- Labels are literal: `_` is doubled (DBusMenu mnemonic), separators are a flag (a `-` label is an item), empty labels stay. A bad icon file keeps the current icon. Item icons go out as `icon-data` only when they are PNG.
- **Depth cap.** Each menu level nests three D-Bus containers, and `dbus-daemon` disconnects a sender whose message nests deeper than 64: a 40-level menu took the whole tray off the bus (the limit falls around 21 levels). One `GetLayout` reply carries at most 16 levels below the requested parent; deeper submenus come without children and a host asking for that subtree gets the rest.
- `nativeDispose` marks the tray closing and returns; the loop closes the connection (the host drops the item at once), frees everything and detaches. Nothing waits for the tray thread.
- On GNOME (`XDG_CURRENT_DESKTOP`) an empty menu advertises `Menu = /`; on Plasma an empty menu gets a lone separator (Kotlin side).

### E2E (Linux)

`./gradlew :tray:test` on a desktop with `dbus-daemon` and `libsystemd.so.0`. Black-box over D-Bus: the test JVM starts a private `dbus-daemon` and points the tray at it (`setenv DBUS_SESSION_BUS_ADDRESS` before the first tray connects); `SniPanel` then plays the panel on it, through JNA bindings to the same sd-bus (`SdBus`): it owns the watcher name and records registrations, reads `IconPixmap` / `ToolTip` / `ItemIsMenu` / `Menu` and `GetLayout`, and calls `Activate`, `Event`, `AboutToShow` as Plasma or the AppIndicator extension do.

- `LinuxTrayTortureTest`: seeded menu fuzzer (shared `MenuFuzzer`: hostile labels, nesting, 0-80 items; compares the layout entry by entry and clicks random entries, checking that only reachable plain / checkable items fire, and their own callback), literal labels, three trays at once (distinct names and ids, isolated callbacks, disposing one keeps the others), duplicate checkable labels (`ItemsPropertiesUpdated`, no `LayoutUpdated`), `ItemIsMenu` and the `Activate` position, icon pyramid (never upscaled, network-order ARGB), garbage icons, stale / impossible events, `onMenuOpened` once per opening, 2000-entry and 40-level menus, an empty submenu, property-only vs structure changes, the GNOME empty-menu path, shortcut hints.
- `LinuxTrayLifecycleTortureTest`: panel restarts and a tray started before any panel, throwing callbacks, a callback updating and disposing its own tray, rapid updates from 6 threads converging on the last one, lifecycle churn, create/dispose x100, 30 trays, callbacks released (weak references collected), the session bus dying under a tray. Every test of both classes ends with no native tray, `NucleusTray-*` thread or item name left (`LinuxTrayTestBase`).
- `LinuxTrayAppE2ETest` (needs `DISPLAY`): `LinuxTrayAppProbeMain` in its own JVM on its own private bus (real `nucleusApplication`, Tao); the probe is also the panel, and reads its popups from the X server (`X11Probe`, Xlib declared by hand: viewable windows with its `_NET_WM_PID`, or named `NucleusStandalonePopup` since Tao's raw popup sets no PID; `_NET_WORKAREA`): click toggles (top panel, then bottom panel against the left edge), `visibleOnStart`, seeded click storm and concurrent `show` / `hide` / `toggle` (state matches the screen), resize, menu, removal, and two `TrayApp`s each anchored to their own icon. Oracle: size, inside the work area, against the top or bottom edge nearer the click, centred on the click x unless clamped.

Run against the old backend (same suite), it found: `_` eaten as a mnemonic, an empty submenu shown as a plain item, the GNOME empty-menu path never switching to `/`, and a process-wide `Semaphore(1)` that let one tray live at a time: the second `initialize` blocked forever inside the initializer's lock, so every later tray call of the JVM hung (all 20 remaining tests timed out). Reading the old code against the protocol showed the rest: one bus name `org.kde.StatusNotifierItem-<pid>-1` and `Id = "1"` for every tray, menu callbacks in one process-wide list keyed by item id (ids restart at 1 per tray; disposing or rebuilding one tray dropped every tray's callbacks), `ItemIsMenu` always true (hosts open the menu and never call `Activate`), no re-registration after a panel restart, one `LayoutUpdated` per item while a menu was rebuilt, a 500 ms join then `free` under a possibly running loop, `-` labels turned into separators, checkables patched by label, a bare `ExceptionClear`.

Fixed in `TrayApp` by the E2E: on Linux the popup was anchored to the last click of any tray (two `TrayApp`s shared one position; it is now per tray), and a popup clamped to the work area's left edge or origin (a left or bottom-left panel) waited out the 3 s anchor timeout before showing (97 ms now): that rejection is a macOS rule (a new status item sits at the menu bar's left edge until it gets a slot) and no longer applies on Linux.

Local runs need `dbus-daemon`, `libsystemd.so.0` and, for the E2E, an X display; the suites skip without them.

Not covered: a real panel drawing the item (the dev machine runs LXDE, whose panel speaks XEmbed, not SNI), Wayland, outside-click dismissal, HiDPI.
