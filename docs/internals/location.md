# location internals

`location` - **Kotlin Multiplatform** geolocation (`jvm`, `android`, `iosArm64`, `iosSimulatorArm64`, `js`, `wasmJs`), modelled on robius-location. `commonMain` holds the API (`LocationProvider` / `Geolocation`) and all the semantics (`BackendLocationProvider`: implicit authorization request, cached-fix acceptance by `maxAge`, timeouts, the cold `locationUpdates` flow); each platform only implements `LocationBackend` — authorization plus *sessions* (fixes and errors between start and stop). Only `jvmMain` uses Rust (`src/main/native`: WinRT `Geolocator`, Core Location on a dedicated `CFRunLoop` thread, XDG Location portal first and GeoClue only when the portal is missing and the app is not sandboxed); Android is the framework `LocationManager` (no Play services; a manifest `ContentProvider` captures the context and the resumed activity, the prompt's answer is read back on the activity's pause → resume), iOS is Core Location through K/N, the web (`webMain`, shared by `js` and `wasmJs`) is `navigator.geolocation` reached through `js()`-bodied helpers only — no external declarations — so one source compiles for both (web tests run on Node; `kotlin-js-store/` holds the yarn locks, refresh with `kotlinUpgradeYarnLock` / `kotlinWasmUpgradeYarnLock`). The module keeps the JVM JNI layout like `share` (`src/main/native`, `src/main/resources` added to `jvmMain`, see [share.md](share.md)). iOS klibs cross-compile on any host (Kotlin 2.4); iOS tests need macOS (`kotlin.native.ignoreDisabledTargets=true`). BCV dumps the `jvm` API only.

Sessions are identified by Kotlin-allocated ids; the native side reserves a slot before starting, so a stop racing the start (a one-shot can finish before `nativeStart` returns) drops the session instead of leaking it. On Windows `authorization()` reports `NotDetermined` until a request in the current process has been answered — WinRT cannot tell "allowed" from "never asked" without asking. On macOS the hardened runtime needs the `com.apple.security.personal-information.location` entitlement for locationd to prompt at all, and desktop apps are granted `authorizedAlways` (reported as `Background`).

`authorizationUpdates()` is implemented once in `BackendLocationProvider`: it polls `LocationBackend.authorization()` (a cheap native status read on every platform, off the collector's thread) and drops repeats, rather than wiring a change signal per platform. `openSettings()` launches a URI or command on desktop (`ms-settings:privacy-location`, `x-apple.systempreferences:…Privacy_LocationServices`, `gnome-control-center location`), the app's settings page on Android / iOS. On Linux only `request_authorization` passes a portal parent to `Start`; sessions start unparented, since a dialog only appears on the first, explicit request.

Linux portal: xdg-desktop-portal (1.21) gets one GeoClue client for all its Location sessions (GeoClue's `GetClient` returns the existing client for the same peer), so a session started while another runs gets no initial fix, each session's thresholds and accuracy overwrite the client's, and closing any session `Stop`s the client under all the others. `linux.rs` therefore runs one portal session per process (`Hub`): every request joins it as a member, new members get the last fix at once, a more precise member reopens it at the higher accuracy (old session closed before the new `Start`), thresholds are filtered per member, and the session is closed with an explicit `Session.Close` when the last member leaves (closing the connection alone is noticed too late by the portal). For host apps the portal grants EXACT without a dialog; sandboxed apps get the Access dialog, which GNOME refuses (`Response` 2) unless the app is focused. `Location services disabled` (GNOME setting / lockdown) arrives as `NotAllowed` from `CreateSession` and maps to `Denied` for the request (sessions classify it `PermanentlyUnavailable`); `isAvailable` creates and closes an unstarted session to see it (closing an unstarted session does not touch the GeoClue client).

Android: on API 31+ the fused provider is driven with an explicit `LocationRequest` — without one it runs BALANCED and never turns GNSS on, so `Precise` asks for `QUALITY_HIGH_ACCURACY`; the one-shot has no platform deadline (30 s by default), the caller's timeout governs. The "asked" flag is written once the prompt is answered, so `authorization()` does not read Denied while the dialog is up. `nucleus-application` reaches `location` as a `compileOnly` dependency, like `share`.

Demos: `examples/location-demo` (console walk through the API on the real platform, desktop), `examples/location-android-demo` (buttons, scriptable with `adb shell am start -n dev.nucleusframework.locationandroiddemo/.MainActivity --es action <request-approximate|request-precise|request-background|fix|cached|track|settings>`, results on logcat tag `LocationDemo`), `examples/location-web-demo` (`jsBrowserDevelopmentRun`). Lab probe: `system.location`, drivable with `-Dlab.probe=system.location?request=foreground&fix&cached&track&settings&accuracy=approximate`.
